SQLiteOrbit · Observation

How OrbitValueObservation turns commits into values

An observation is a fetch plus a description of what to do with its results. Started on a database, it gets a runtime, shared by every subscriber to that observation on that database. The runtime records which columns each fetch reads, registers that region with the database, and fetches again when a commit touches it. A write through the observed handle is fetched inside its own transaction, just before it commits. Every other commit goes to a refetch controller. The scenes follow the code in Sources/SQLiteOrbit/Observation/ step by step, and scene 10 lists the tests that pin each guarantee.

How a commit reaches another process is covered on its own page: the Unix datagram IPC transport.

01

Architecture map

The parts of one observation and what it is started on. Tap or hover a component to see what it does and where it lives. The steps follow one observation from subscribe to its first value, then one commit from another process to a callback.

02

Recording what a fetch reads

An observation watches the columns its fetch read, and SQLite is what says which ones those are. Pick how the observation was made: tracking(_:) records every fetch, trackingConstantRegion(_:) records only the first, and tracking(region:_:) never records.

03

A write through the observed handle

When this process writes through the database the observation subscribed to, the runtime finds out before the commit, and fetches on the writing transaction itself. The value is ready when the commit lands, and no second read is needed. Pick a write to see each way it can end.

04

Commits from anywhere else

Every other commit is reported only after it has happened: one by another handle on the same database in this process, one by another process, and one this handle made outside a transaction. All three end in requestRefetch, which records what is outstanding and starts the refetch controller.

05

Refetch controllers

A refetch controller decides when an invalidated observation fetches again, and whether a fetch that a newer commit made stale may still be published. Set one with refetching(_:). Only one runs at a time for each runtime, and each fetch is tagged with the revision it started at.

06

Advertisement and floors

A database that filters by region can skip a commit outside what the observation registered. So the runtime tracks, for every fetch, the region that was registered the whole time the fetch ran, and a fetch that read outside it is never trusted as the last word. The rule comes first, then four cases. The other side of this, a process that skips a peer whose marker doesn't cover a commit, is scene 09 of the IPC page.

The floor ruleA fetch counts only if the region it read was registered for its whole duration.Only for databases whose subscription filters by region. Any other database is registered for .fullDatabase throughout.
The floor
advertisement.beginFetch() runs before a fetch takes its snapshot and records the registered region as that fetch's floor. endFetch returns it. Until a fetch has said what it reads, the registration is .fullDatabase, or the constant region of tracking(region:_:).
Narrowing counts at once
beginUpdate(to:) intersects the region, and every live floor, with the target as soon as the update is decided, since the database may honor a narrower region at any moment.
Widening counts afterwards
Only once updateRegion(_:) has returned, and every announcement that starts afterwards honors the new region, does finishUpdate(to:) set it.
Covered
In accept(…), a fetch is covered if floor.contains(output.region). A covered fetch is published.
A refetch that isn't covered is withheld
A refetch controller's fetch that read beyond its floor, unless forced, is not published. Its read region joins observedRegion, a refetch is required again, and the controller is told .superseded.
Any other fetch owes a covering fetch
An initial read or a local write's fetch that read beyond its floor is published, and sets owesCoveringFetch. Once the registration covers what it read, the runtime asks for a refetch as if another process had committed.
Widen, wait, then read
advertiseObservedRegion() runs after every accepted or withheld fetch, outside the state lock and one at a time. It applies beginUpdate, updateRegion and finishUpdate until the registration matches observedRegion, and only then asks for an owed fetch.
Narrowing to what was read is safe
Nothing outside the region a fetch read can change its value. If updateRegion throws, the observation ends with that error.
07

The initial value, and sharing a runtime

The first subscriber creates the runtime and registers it with the database before anything is read, so a commit can't fall between the first read and listening. Pick how the initial value is fetched, what a later subscriber gets, and what happens when a commit lands during the first read.

08

Operators and delivery

An accepted fetch goes through the operator chain, then to every subscriber through its own scheduler, in order. Pick an outcome: a value, a value an operator suppressed, a failure, which ends the observation, or a subscriber that cancels with a callback still queued.

09

Observable values a fetch reads

A fetch can depend on more than the database, such as a search field or a filter toggle. On systems with Observation, the runtime records the observable properties each fetch reads and fetches again when one changes. OrbitExternalValue holds such a value safely across threads, and notices changes one field at a time.

10

The tests that pin it

Which tests hold the value observation to each guarantee the scenes describe, and how each one brings about the failure it guards against. They are Swift Testing tests in Tests/SQLiteOrbitTests/, most of them in Observation/; the path under each name is relative to that directory. Most are built with the StructuredQueries trait and one of the SQLite backends. A tag says what the test is set up with. A test tagged process runs the test executable again as a helper, a process of its own with a real transport. gate holds a fetch open, so that another commit lands while it is in flight. An announcing database is one whose commits the test announces itself, with any origin and region, whenever it chooses. in-memory IPC is a network of InMemoryIPCTransports, with a second transport standing in for another process, and unix datagram is real sockets. pure state drives one of the observation’s internal state machines with no database at all. Turso trait needs the Turso backend. A tag with a · lists the arguments a parameterized test runs with.

How UnixDatagramIPCTransport tells other processes a transaction committed

Every process that opens an OrbitIPCDatabase joins a shared coordination directory, binds one Unix datagram socket, and advertises the regions it cares about in marker files. A commit is sent only to the peers whose advertised region it concerns. The backpressure policy is never block, never drop a change: a send never waits, and a peer with no room is owed the commit's region instead. One event-loop thread per transport receives datagrams and sends full peers what they are owed, with no broker and no Dispatch. Scene 10 lists the tests that pin each of these guarantees, and how each one brings about the failure it guards against.

Discovery through the coordination directory

Processes find each other through the filesystem: sockets in v1/s/, and one marker per endpoint per database in v1/d/<coordinationKey>/. Markers are replaced whole with a rename. 06

Backpressure: owed regions for full peers

What the transport does when a peer can't keep up. The policy is summed up first, and the animation below shows how it works. Pick a scenario to see each way an owed region ends: it is delivered, the peer stops advertising the database, or the peer turns out to be dead. Scene 07 shows the rest of what happens when a peer dies.

Backpressure policyNever block, never drop a change: a full peer is owed a region.It is the only policy, and there is nothing to configure.
A sender never waits
Every socket is nonblocking, and send returns as soon as each concerned peer has been offered the datagram. It is async only because the protocol requires it.
Who counts as full
EAGAIN, EWOULDBLOCK or ENOBUFS → .full: the peer is owed the region. ENOENT, ECONNREFUSED, ECONNRESET or ENOTCONN → .peerGone: the peer's path is connected to once more, and only if nothing is bound there is the peer dead and pruned (scene 07). Any other error → .failed.
Memory is bounded, order is kept
A peer is owed at most one region per database. Later commits are merged into it without a send attempt, so a full peer is never sent a new commit ahead of what it is owed.
Merging loses no change
An owed region only widens. The peer hears fewer, broader commits and refetches more, but it never misses a change.
Recovery
What a peer is owed goes out in batch datagrams once it has room. Linux and Android learn that from EPOLLOUT. Darwin's write filter can't see the receiver's queue, so it retries on a backoff: 1 ms, doubling up to 1 s.
No deadline, no drop-oldest
An owed region ends only when it is delivered, when the peer withdraws its marker (the sender applies this at its next send to that database), when the peer is found dead, or when a flush fails with some other error. In the last two cases it is dropped.
What the caller sees
send succeeds when every concerned peer either took the datagram or is now owed it (deferredPeerCount). It throws UnixDatagramIPCTransport.PartialDeliveryError only if a live peer couldn't be sent to at all. The error carries the discovered, delivered, deferred and failed counts. Dead peers are pruned and not counted.
Why not block, wait or drop
Blocking the writer, or waiting with a timeout, would let one slow or suspended peer stall every writer. Dropping a message would lose an invalidation and leave the peer's observations stale.
07

Crashes, cleanup and repair

What happens to the files in the coordination directory when a process dies, and when a live process's files are removed from under it. Only a probe decides whether an endpoint is dead, as summed up first. Pick a scenario: a crash that the next transport to start sweeps up, a send that finds a peer dead, a peer that only rebound its socket, and a live endpoint whose files were deleted and which puts them back.

DefinitionAn endpoint is dead if and only if nothing is bound at its socket's path.Nothing else counts: not age, not silence, not a full queue.
The probe
UnixDatagramSocket.probe(_:) connect()s a new datagram socket to v1/s/<name>.sock. That sends nothing, and the owner never hears about it. Only ECONNREFUSED (a file with no socket bound to it) or ENOENT (no file at all) returns .dead.
Everything else is alive
A suspended, stopped or busy process still holds its socket, and a full queue doesn't refuse a connect. Any other error, even a failure to try at all, counts as .alive. Taking a live endpoint for dead would cost it its files, while taking a dead one for alive only puts off removing them.
No timers, heartbeats or leases
Nothing is dead because it is old or quiet. The one exception is a hidden .<name>.sock, which exists only while a bind is under way: it is removed once it is dead and more than 60 s old.
A visible socket is always bound
Sockets are bound under the hidden name and renamed into place, so a probe never catches a .sock whose bind is still under way.
Who removes the dead
Each transport as it starts: UnixDatagramStaleCleanup.sweep, under v1/cleanup-stale.lock. A send, or the endpoint's thread, that finds a peer dead: registry.prune(_:). Both remove its socket's file, its marker and .tmp in every database, and each database directory left empty.
A sweeper that dies or freezes
No one ever waits for cleanup-stale.lock: a sweep that finds it held skips, so a stopped holder only delays cleanup, and never holds up a transport's start. A holder that dies loses the flock with its descriptors, and the next sweep takes the file it left and unlinks it. A sweep only removes, one unlink or rmdir at a time, so one cut short leaves nothing half done. It probes an endpoint again right before removing each of its files, so a sweeper that was frozen for hours never acts on what it found before.
.peerGone is not proof
A connected socket that reports its peer gone only shows that the socket it was connected to closed. The path is connected to once more first. If something is bound there, that is the peer, and it keeps what it is owed.
A live endpoint puts its files back
If its socket's file or markers are removed anyway, by the system, by hand, or by a peer that took it for dead, its own directory watch wakes its thread. The thread binds a new socket at the same path and writes its markers again. Peers may have left the endpoint out of commits in the meantime, so it then tells its own subscribers that each of their databases may have changed, with a full-database commit.
So that they don't look unused
Every send and every receive touches the endpoint's socket, its markers and their directories, at most once an hour, so macOS's temporary-file cleaner, which deletes files unused for about three days, leaves them alone.
08

The event loop: Darwin and Linux/Android

One “Orbit IPC” DetachedThread per transport blocks in UnixEventQueue.wait(until:). The two platforms differ in one important way: Linux can report when a full peer has room, and Darwin can't, so Darwin retries on a timer that backs off to once a second. The thread also waits on its registry's own directory watch, which tells it when the endpoint's files change (scene 07).

09

Region widening for value observations

An observation whose fetch reads more than it had advertised must not miss a commit to the new part. It widens its advertisement first, and updateRegion(_:) returns only after the new marker is on disk. Then it reads again. Compare the real order with the order that would lose a commit.

10

Robustness, and the tests that pin it

Which tests hold the transport to each guarantee the scenes describe, and how each one brings about the failure it guards against. They are Swift Testing tests in Tests/SQLiteOrbitTests/IPC/UnixDatagram/. A test tagged process runs the test executable again as a helper, a process of its own with its own transport, which the test can stop with SIGSTOP, resume with SIGCONT or kill with SIGKILL. A held handler is a subscription whose handler blocks the transport's thread at its first message, as a suspended process would, so its socket's queue fills and it repairs nothing until the test lets it go.
